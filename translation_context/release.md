## 发版检查清单

1. 确认目标游戏版本，并核对反编译源与 `translation_context` 中记录的行号、ID 是否仍匹配。
2. 运行完整审计（与 CI 相同的命令，见 [index.md](index.md)），要求全部退出码为 0。
3. 确认没有残留的 STALE 记录：`python tools/audit_manual_coverage.py` 应报告 0 个过期文件、0 个缺失文件。
4. 更新 `CHANGELOG.md`，写清本版面向的游戏版本、翻译改动和已知限制。
5. 在隔离的匹配版本游戏副本中构建并校验 RPA（`tools/build_rpa.py --require-compiled`），不要直接对用户的游戏目录操作。
6. 发布后在 Release 说明中写明：对应游戏版本、安装路径（`game/zh_hans.rpa`）、已知问题，以及不要与散装 `tl/zh_hans` 同时安装。

## 同游戏版本官方原包复用

在Actions的Build Chinese RPA中手动生成新发行版时，`official_package`提供四种选择：

| 选项 | 行为 | 存储影响 |
| --- | --- | --- |
| 复制并仅保留最新原包（默认） | 先复制并验证同游戏版本的各平台原包；全部完成后删除旧发行版的对应原包附件 | 迁移期间暂时存在多份，完成后同游戏版本原包仅保留在最新发行版 |
| 复制官方原包 | 从之前同游戏版本、最近发布且含官方原包的非草稿发行版下载，并校验后上传到新发行版 | 每次新增独立附件记录及相应下载/上传流量；不假定GitHub底层去重 |
| 引用原包下载链接 | 保留新发行版汉化包，在发行说明中添加旧原包的直达链接 | 不重复上传原包；需要保留源发行版及附件 |
| 不复用 | 只发布汉化包 | 原包可另行手动上传 |

游戏版本必须精确匹配，7944与8194不能互相复用；同版本的T/P/R发行版均可作为来源，不跨游戏版本，跳过当前目标和草稿。若最近发行版只有汉化包，则向前查找最近含原包的发行版。首次出现某游戏版本、没有可用来源时仍发布汉化包并提示手动上传原包一次。

“复制并仅保留最新原包”按同游戏版本、同附件名分别选择最近的原包，包含只存在于较早发行版的平台包。全部原包下载、上传及SHA-256校验通过后，重新查询目标和旧发行版；目标必须仍包含已验证的附件，且没有更新的同版本非草稿发行版（即使该版尚无原包）。先检查所有旧附件与目标的名称、大小、摘要，再删除匹配的旧原包附件，保留旧发行版本身、说明和汉化包。校验失败、摘要缺失、旧包内容不同、目标附件改变或平台包尚未迁移时，不开始清理；复制中断也不删除旧包。删除途中API失败会使任务失败，目标已验证原包仍保留。

旧发行说明如果曾引用已删除原包的固定链接，该链接会失效；需要旧链接持续有效时选择不删除的“复制官方原包”或“引用原包下载链接”。默认迁移模式与长期保留旧下载链接不能同时保证。本规则用于后续手动发包，不主动删除现有发行版附件。

原包附件采用官方命名形式，例如`summertimesaga-21.0.0-wip.8194-pc.zip`；只复用版本匹配的summertimesaga压缩包/安装包，不复制zh_hans.rpa或仓库自动生成的源码压缩包。支持zip、7z、apk、exe、dmg、tar.gz、tar.bz2、tar.xz，平台部分保留原名。准备步骤在新发行版创建前固定来源，随后逐个下载/上传，校验大小以及API提供的SHA-256；目标已有同名附件且摘要一致时跳过，冲突则失败，禁止覆盖原包。

原包不写入Git仓库，也不作为Actions长期Artifact保存；临时文件仅在发布任务运行期间存在。发布任务超时改为30分钟以容纳大文件传输。release published触发仍只更新汉化附件，此复用功能仅用于workflow_dispatch生成新发行版。

GitHub当前文档规定单个Release附件小于2GiB，每个Release最多1000个附件，不限制Release总大小和下载带宽；底层物理去重是否发生没有公开保证。若希望避免每次重复保存约1.43GB的8194原包，可选择“引用原包下载链接”。依据：[GitHub Release配额说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas)。

实现与验证：`tools/reuse_official_package.py`、`tools/test_reuse_official_package.py`；自动化测试覆盖同版本来源选择、跨版本隔离、草稿/目标排除、首次发布、多个平台、大小/摘要校验、链接幂等及复制/冲突流程。已对现有8194-R2做真实API只读来源查询；未触发新发行版或实际复制大附件，真实上传链路在后续手动发包时验证。

## 构建产物现状

重发已有发行版时，在发包Actions的`existing_release`填写完整标签，例如`v21.0.0-wip.8194-R4`，游戏版本与发布类型必须匹配。工作流验证目标已发布且预发行状态一致，重新编译并覆盖两个RPA附件，保留标签、原包附件和更新说明，不分配新编号，也不执行原包迁移。留空仍按原规则创建下一个编号。

发包Actions从同一份编译后的`build/game`生成两个附件：`zh_hans.rpa`保留现有行为，包含翻译与`mods/`脚本；`zh_hans_no_mods.rpa`使用`tools/build_rpa.py --exclude-mods`，只收集`tl/`资源，排除所有`mods/`条目。无Mod包保留翻译所需的字体、语言入口、短信和更新日志等辅助脚本。两份包分别检查编译产物齐全，并对索引及文件内容进行校验；Artifact上传、已有Release更新和新编号Release创建均包含两个附件。安装时二选一，无Mod包下载后改名为`game/zh_hans.rpa`，先移除旧包及重复散装Mod；已有存档后果不随换包自动回退。

`tools/test_build_rpa.py`覆盖翻译资源逐字一致、Mod目录排除、含Mod包误当无Mod包时拒绝、内容改变时拒绝、所选包编译缺失检查及CLI验证模式。旧发行版不自动补发无Mod附件，是否包含新附件以发行页实际内容为准。

- `dist/zh_hans.rpa` 与 `dist/chinese.rpa` 是历史构建产物，可能落后于当前翻译源。构建时间见文件修改时间，最新翻译改动时间见 `git log -1`。
- 判断产物是否过期：比较 `dist/zh_hans.rpa` 修改时间与 `tl/zh_hans` 中最新的改动时间；不一致时以翻译源为准。
- 默认不把构建产物提交进改动；正式发布由 `.github/workflows/build-chinese-rpa.yml` 在 Release 触发时生成。
- `.codex_tmp/` 是本地临时目录，不进入版本管理，也不参与发布。

## 上游游戏更新时的处理

1. 用 `tools/audit_source_comments.py --source-root <新版反编译目录>` 核对源注释与对白摘要，先定位行号漂移的翻译块。
2. 以引擎实际翻译节点的 filename 与 linenumber 为准调整块位置，不按反编译文本的物理行号猜测。
3. 检查引擎报告的 orphan 清单，确认哪些旧块已不再使用；删除前同时检查 `sentence_patterns.json` 是否仍有对应原文。
4. 新增对白按 [style_guide.md](style_guide.md) 的提取文本维护规则归档，并同步 `manual_review.json` 的哈希与行号。
5. 在 `CHANGELOG.md` 与上表登记新的游戏版本与汉化版本对应关系。
6. 按[index.md的新增规则入口](index.md#新增规则查阅入口)复查新版所有同类文本：对话按钮标点、设置悬浮说明、回归提示模板、鸣谢用户名、联系人姓名和六类身份标签。使用新版源字符串与当前映射的差集发现漏译，不只检查既有中文文件或用户截图。
7. 对照本体重新核对`tel_cast`、`tel_conv`及设置显示入口，合并上游布局、参数、动作和类别变化；确认GitHub图标资源随包分发、位置正确且链接目标固定。分别记录字符串查询、中英切换、组件渲染、真实悬浮和完整导航的验证范围，未完成项继续保留。
